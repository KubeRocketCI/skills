# Vocabulary and naming

The portal and the krci CLI use delivery terms. The cluster stores custom resources. Users speak the first language, kubectl speaks the second.

## Term map

| Portal and CLI | Custom resource | API group | Notes |
|---|---|---|---|
| Project | `Codebase` | `v2.edp.epam.com` | `spec.type` is `application`, `library`, `autotest`, `infrastructure`, or `system` (the GitOps repository). The CRD has no enum, the portal sets the value. |
| Branch | `CodebaseBranch` | `v2.edp.epam.com` | The resource name is derived from the branch name, and branches created in the portal get a random suffix. Select by label instead of building the name. |
| Image versions | `CodebaseImageStream` | `v2.edp.epam.com` | One per branch. `spec.tags[]` grows with every successful build. |
| Deployment, deployment flow | `CDPipeline` | `v2.edp.epam.com` | `spec.applications` lists the projects it delivers. |
| Environment | `Stage` | `v2.edp.epam.com` | Named `<deployment>-<environment>`. `spec.order` defines the promotion sequence. |
| Deployed application | `Application` | `argoproj.io` | Named `<deployment>-<environment>-<project>`. Lives in the platform namespace, not in `argocd`. |
| Pipeline run | `PipelineRun` | `tekton.dev` | Review, build, deploy, clean, security, tests, and release runs are all PipelineRuns. |
| Manual approval | `ApprovalTask` | `edp.epam.com` | A pending approval is a blocking task inside a deploy run. |
| Queued run | `PipelineRunQueue` | `edp.epam.com` | Explains a run that waits in `PipelineRunPending`. |
| Git server | `GitServer` | `v2.edp.epam.com` | `status.connected` tells whether the platform reaches the provider. |
| Quick link | `QuickLink` | `v2.edp.epam.com` | Links to SonarQube, Argo CD, logging, and monitoring. |

## Namespaces

- **Platform namespace**: holds every custom resource above for one tenant. Its name is chosen at install time.
- **Environment namespace**: holds the workloads of one environment. It is recorded in `Stage.spec.namespace`, required and immutable. The default, which the portal fills in, is `<platform-namespace>-<deployment>-<environment>`.
- An environment can target another cluster. `Stage.spec.clusterName` is `in-cluster` for the platform cluster, otherwise the name of a registered cluster.

## Labels worth selecting on

| Label | On | Value |
|---|---|---|
| `app.edp.epam.com/codebase` | CodebaseBranch | project name. `app.edp.epam.com/codebaseName` carries the same value and is deprecated. |
| `app.edp.epam.com/stale` | CodebaseBranch | set when the branch is marked stale |
| `app.edp.epam.com/cdPipelineName` | Stage | deployment name |
| `app.edp.epam.com/pipeline`, `app.edp.epam.com/stage`, `app.edp.epam.com/app-name` | Argo CD Application | deployment, environment (not the Stage resource name), project |
| `app.edp.epam.com/codebase`, `app.edp.epam.com/codebasebranch` | PipelineRun | project, branch resource |
| `app.edp.epam.com/pipelinetype` | PipelineRun, Pipeline, TriggerTemplate | `review`, `build`, `deploy`, `clean`, `security`, `tests`, `release` |

## Where a resource says what is wrong

| Resource | Field |
|---|---|
| Codebase, CodebaseBranch | `status.status`, `status.result`, `status.detailedMessage` |
| CDPipeline, Stage | `status.status`, `status.result`, `status.detailed_message` |
| GitServer | `status.status` (`ok` or `failed`), `status.connected`, `status.error` |
| Argo CD Application | `status.health.status`, `status.sync.status`, `status.conditions[]`, `status.operationState` |
| PipelineRun, TaskRun | `status.conditions[0]`, then the failed step in `status.steps[]` |

The two spellings of the detailed message field are both correct. They differ by resource kind.

## Environments

- `Stage.spec.triggerType` is `Manual` (the default), `Auto` (deploy every new build), or `Auto-stable` (deploy the new build, keep the other applications on their stable versions).
- `Stage.spec.triggerTemplate` names the deploy pipeline and defaults to `deploy`. `Stage.spec.cleanTemplate` is optional.
- Quality gates are in `Stage.spec.qualityGates`: a manual approval, or an autotest project and branch.

## Delivery contract of an application repository

- A `Dockerfile` at the repository root builds the image.
- A Helm chart in `deploy-templates/` deploys it.
- Every successful build tags the repository. The tag and the image version depend on `Codebase.spec.versioning.type`:

  | Versioning | Git tag | Argo CD target revision |
  |---|---|---|
  | `semver` | `build/<version>` | `build/<version>` |
  | `default` | `<branch>-<timestamp>`, equal to the image tag | the image tag |
  | `edp` (deprecated) | `build/<version>` | the image tag |

- Argo CD Applications are generated by one ApplicationSet per deployment flow, named after it, in the platform namespace. The deploy run sets the Helm parameters `image.tag`, `image.repository`, and `image.digest`.
- Per-environment overrides live in the GitOps repository at `<deployment>/<environment>/<project>-values.yaml` and apply only when the deploy runs with values override.
- Build and review pipelines are chosen by name from the project's Git provider, build tool, framework, type, and versioning. `CodebaseBranch.spec.pipelines` shows the names in effect.
- Build pipelines run as the `tekton` service account, other pipelines as `tekton-unprivileged` unless the Pipeline sets the annotation `app.edp.epam.com/service-account`.
